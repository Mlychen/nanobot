# 学习助手并行执行规则

本文档用于约束第一阶段多人并行开发时的执行方式。

目标不是讨论功能设计，而是控制并行开发中的粒度、冲突、联调顺序和上游兼容风险。

---

## 一、基本原则

1. 一包一分支，一包一 PR
2. 不允许跨工作包顺手实现额外需求
3. 新增模块优先，热点文件最后接线
4. 任何实现都必须服从工作包边界，而不是反过来扩张工作包
5. 若某项需求超出当前工作包定义，先更新文档，再改代码

---

## 二、适用范围

本规则适用于以下工作包：

1. `WP00-协议与边界`
2. `WP01-身份统一层`
3. `WP02-会话策略层`
4. `WP03-PrimaryAgent编排层`
5. `WP04-DomainAgentRuntime`
6. `WP05-通知路由`
7. `WP06-SchedulerAgent`
8. `WP07-学习模式与技能`

## 三、完成度跟踪清单

### 1. 使用目的

本清单是第一阶段并行实施的唯一公开进度面板。

要求：

1. 每个执行者开工前必须先在本清单认领自己的工作包
2. 每次状态变化都必须先更新本清单，再继续提测、联调或提 PR
3. 总体进度、门禁判断、联调排期一律以本清单为准
4. 若代码状态与清单状态不一致，以“清单未更新”视为未完成

### 2. 状态口径

统一只允许使用以下状态：

1. `未开始`：尚未开工，或只有想法没有实际提交
2. `开发中`：已经开始编码，但还未达到本包自测完成
3. `代码完成`：代码、测试、文档已在本包范围内补齐，等待联调或合并
4. `联调中`：本包代码完成，正在进行 Gate 联调或依赖联动验证
5. `阻塞`：存在外部依赖、接口冲突、环境问题，当前无法继续推进
6. `已完成`：满足本文“完成定义”，并且不再阻塞后续工作包

补充说明：

1. `代码完成` 不等于 `已完成`
2. 只有通过对应 Gate 或确认不需要 Gate 的工作包，才允许标记为 `已完成`
3. `阻塞` 必须写清楚阻塞原因、依赖对象和恢复条件

### 3. 更新时机

以下情况必须更新一次清单：

1. 认领工作包时
2. 开始编码时
3. 提交 PR 前
4. 进入联调时
5. 联调通过时
6. 发现阻塞时
7. 阻塞解除时

### 4. 每次更新必须填写的字段

1. `责任线程/执行者`
2. `分支`
3. `状态`
4. `最近产出`
5. `阻塞或风险`
6. `下一步`
7. `最近更新`

### 6. 总体完成判断

总控可按以下方式快速判断项目进度：

1. `WP00` 完成后，才允许判断波次 A 结束
2. `WP01 + WP02` 至少进入 `联调中`，才允许安排 Gate A
3. `WP03 + WP04 + WP05` 至少进入 `代码完成`，才允许安排 Gate B
4. `WP06 + WP07` 至少进入 `开发中`，才允许启动波次 C 周会
5. 只有 `WP06 + WP07` 都达到 `已完成`，才允许宣称第一阶段功能闭环完成

### 7. 执行纪律

1. 不允许把“本地写了代码但没推分支”标记为 `代码完成`
2. 不允许把“测试没跑、文档没改”标记为 `代码完成`
3. 不允许把“尚未过 Gate 联调”标记为 `已完成`
4. 不允许把“等待别人帮忙”写成空白；必须明确写出依赖哪个 WP
5. 若连续两个工作日未更新自己负责行，默认视为进度失联，需要总控介入

## 四、分支规则

### 1. 分支命名

统一使用：

1. `wp00-protocols`
2. `wp01-identity`
3. `wp02-session-policy`
4. `wp03-primary-orchestrator`
5. `wp04-domain-runtime`
6. `wp05-notification-router`
7. `wp06-scheduler-agent`
8. `wp07-learning-modes`

若同一工作包需要补充修复，使用：

1. `wp01-identity-fix-1`
2. `wp05-notification-router-fix-1`

### 2. 建分支规则

1. 一律从最新 `main` 切出
2. 切分支前先同步上游主分支
3. 不允许从其他工作包分支继续切新分支

## 五、PR 规则

### 1. 粒度要求

每个 PR 只能对应一个工作包。

PR 内允许包含：

1. 当前工作包代码
2. 当前工作包测试
3. 当前工作包文档更新

PR 内不允许包含：

1. 其他工作包的实现
2. 与本包无关的重构
3. 风格化清理型大面积改动

### 2. PR 标题规则

统一使用：

1. `WP01: add identity mapping foundation`
2. `WP03: add primary agent orchestrator skeleton`

### 3. PR 描述必须包含

1. 工作目标
2. 改动边界
3. 修改了哪些热点文件
4. 跑了哪些测试
5. 未解决问题和后续依赖

---

## 六、热点文件管理

以下文件是第一阶段的热点文件：

1. `nanobot/cli/commands.py`
2. `nanobot/agent/loop.py`
3. `nanobot/session/manager.py`

### 1. 允许修改热点文件的工作包

1. `WP01`
2. `WP02`
3. `WP03`
4. `WP05`

### 2. 原则上不应修改热点文件的工作包

1. `WP04`
2. `WP06`
3. `WP07`

### 3. 修改规则

1. 修改热点文件必须是打点式接线
2. 不允许在热点文件中堆业务逻辑
3. 一个 PR 若同时修改两个以上热点文件，必须说明原因
4. 若一个工作包必须临时修改不属于自己范围的热点文件，应先停下并更新文档边界

## 七、合并顺序

### 1. 波次 A

先合并：

1. `WP00`

要求：

1. 协议冻结后，其他工作包才可以开始正式代码实现

### 2. 波次 B

可并行开发、分批合并：

1. `WP01`
2. `WP02`
3. `WP03`
4. `WP04`
5. `WP05`

合并建议顺序：

1. `WP01`
2. `WP02`
3. `WP04`
4. `WP03`
5. `WP05`

原因：

1. 先稳住身份与 session
2. 再稳住 domain runtime
3. 然后接主控编排与通知出口

### 3. 波次 C

在波次 B 稳定后合并：

1. `WP06`
2. `WP07`

## 八、联调规则

### 1. Gate A

联调范围：

1. `WP01 + WP02`

通过标准：

1. Feishu 与 CLI 身份映射可用
2. 群聊/私聊 session 不串
3. 旧 session 文件可继续使用

### 2. Gate B

联调范围：

1. `WP03 + WP04 + WP05`

通过标准：

1. 主 agent 能做 sync/async/event 三类路由
2. domain agent registry 可接入 orchestrator
3. 异步结果可走通知路由输出

### 3. Gate C

联调范围：

1. `WP06 + WP07`

通过标准：

1. scheduler agent 可稳定运行
2. 至少两个学习模式可用
3. 主动提醒链路稳定

---

## 九、测试规则

### 1. 每个工作包最低要求

每个工作包合并前必须至少提供：

1. 单元测试
2. 必要的集成测试
3. 对现有主流程的最小回归验证

### 2. 热点文件相关工作包

`WP01/WP02/WP03/WP05` 除本包测试外，还必须补一组回归验证，确保：

1. 现有 CLI 主流程未破坏
2. 现有消息处理主流程未破坏
3. 现有 session 存储主流程未破坏

### 3. 业务工作包

`WP06/WP07` 合并前必须证明：

1. 不依赖未定义协议
2. 不要求额外重构底层 runtime

### 4. Windows CLI 编码约束

Windows 环境下，`uv run python -m nanobot.cli.commands agent ...` 与 `uv run python -m nanobot.cli.commands gateway ...` 可能因为 Rich logo 或 emoji 输出触发 `UnicodeEncodeError`（常见于 GBK 控制台）。

Gate B 及后续联调默认遵循以下规则：

1. 主链路验证优先使用 API 级 runtime 测试，不把 CLI logo 输出当成业务阻塞
2. 如需执行真实 CLI/gateway 冒烟，必须显式使用 UTF-8 控制台，或采用无 emoji 输出方案
3. 若遇到 Rich/GBK 输出异常，必须在验收记录中注明“编码环境问题”，不得误判为 orchestrator 或 router 逻辑故障

## 十、文档同步规则

### 1. 每个工作包变更时必须同步的文档

至少同步：

1. 自己的工作包文档
2. 若边界有变化，同步 `学习助手并行实施总览.md`

### 2. 禁止行为

1. 代码改了，文档不改
2. PR 里顺手改别的工作包文档但不说明原因

---

## 十一、冲突处理规则

### 1. 发现越界

如果一个工作包在实现时发现必须改别的工作包职责范围：

1. 先停止扩写代码
2. 回到文档核对边界
3. 若确实需要调整，先改文档，再继续实现

### 2. 多包同时争用热点文件

处理顺序：

1. 先合并依赖更基础的工作包
2. 后续工作包 rebase 到最新 `main`
3. 不允许通过“临时一起改”解决冲突

### 3. PR 冲突扩大

如果 rebase/merge 时冲突已经扩散到：

1. provider
2. MCP
3. 具体 channel 实现

则应判定为架构越界，而不是继续硬解冲突。

---

## 十二、上游同步规则

### 1. 开发前

1. 每个工作包开工前先同步最新 `main`

### 2. 合并前

1. PR 合并前必须 rebase 或 merge 最新 `main`
2. 必须重新跑本包测试

### 3. 异常处理

1. 若上游改动导致本包接口失效，优先收敛到新增模块修复
2. 不要为了兼容上游，在热点文件里临时堆逻辑

---

## 十三、完成定义

一个工作包被视为“完成”，必须同时满足：

1. 代码实现完成
2. 测试通过
3. 文档同步完成
4. 未越过本包边界
5. 能在当前 `main` 上干净合并

若只完成了代码但不满足以上条件，视为“开发中”，不能进入下一门禁。
